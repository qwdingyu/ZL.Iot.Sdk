# ZL.ProtocolGateway 缺陷修复记录（场景测试首次真实运行暴露）

日期：2026-10-07
背景：`tests/ZL.ProtocolGateway.Tests` 从未进入 IoT.Sdk.sln / CI，长期无人运行。
本次首次完整运行（1374 用例）暴露 5 个**产品缺陷**与一批测试自身错误，逐一定位并修复。
修复后：**1372/1374 通过**；剩余 2 个为既有失败（见 §3）。

## 1. 产品缺陷（5 个，均已修复并有验证）

### 1.1 GatewayService 兼容构造是空壳 —— 消息静默全丢
`GatewayService(IPipeline pipeline)` 注释写着「将传入 pipeline 的输出插件迁移到 manager」，
但方法体只剩一行「仅保留兼容构造」的注释。传入的 pipeline 成为孤岛：其输出永不启动
（连连接循环都不跑）、路由规则不生效；输入消息进入 manager 内部 pipeline 后无路由可匹配
而被静默丢弃。所有经此构造 + `pipeline.RegisterOutput/AddRouter` 的调用方（6 个场景测试
与 NuGet 包消费者）转发**全部静默失效**。
修复：恢复迁移语义——输出经 `GatewayManager.RegisterOutput`（内部会同步注册进 manager 的
pipeline，随 StartAsync 启动）、路由规则加入 `manager.Pipeline`；为迁移新增
`MessageRouter.Rules` 与 `ResilientMessagePipeline.RegisteredRouterRules` 只读访问器。
验证：Tcp 转发场景 3 败 → 8/8 全过。

### 1.2 InputPluginBase.StopAsync 顺序导致停机死锁
原顺序：先 `await OnStopAsync()`，finally 里才 `_cts.Cancel()`。而子类 OnStopAsync 普遍要
`await` 由该令牌驱动的接收/轮询循环 → 循环等令牌、OnStopAsync 等循环，**三方互等死锁**，
StopAsync 永不返回。manager 路径此前「碰巧」不死（manager 先取消了自己链入的令牌），
直接调用 `plugin.StopAsync()` 的路径（测试、嵌入式用法）必死。
修复：先取消令牌、再停插件。
验证：UdpInput 场景测试此前无限挂死（整轮测试跑不完），修复后 81ms 通过。

### 1.3 UdpInputPlugin 停止后 NRE 空转刷日志
OnStopAsync 把 `_udpClient` 置 null 后，接收循环仍解引用该字段 → 每 100ms 一条
`Receive error: Object reference not set...` 无限刷（与 1.2 叠加成挂死）。
修复：循环内取本地快照并在 null 时退出。

### 1.4 工业输出插件「连接活着时永远拒绝发送」（5 个插件）
`ModbusTcp / AllenBradley / IEC61850Mms / MitsubishiMc / OpcUa` 的 `TryConnectAsync` 均为
「建连后持有连接直到断开才返回」，而基类外层循环在 TryConnectAsync **返回后**才置
`Status = Running` → 连接活着期间状态恒为 `Starting`，`OutputPluginBase.SendAsync` 的
`Status != Running` 守卫拒绝一切发送：**发送要求 Running、Running 要求连接断开，互锁**。
实测（ModbusTcp + 本地 mock）：连接建立后 Status 停在 Starting，SendAsync 连续 12 秒全被拒、
对端一帧未收。
修复：`IndustrialOutputPluginBase.MarkConnectionEstablished()`（置 Running + 发布 Healthy），
外层循环改调它，5 个长持有插件在建连成功处调用。
验证：Modbus 发送 51ms 成功、mock 收到 12 字节帧；场景测试 2/2 过。

### 1.5 HttpInputPlugin 拒绝一切自定义路径前缀
`HttpListener.Prefixes` 要求前缀以 `/` 结尾，插件直接拼接 `PathPrefix`（如 `/api`）→
`ArgumentException: Only Uri prefixes ending in '/' are allowed`，**任何非默认前缀都无法启动**。
修复：拼接前补尾斜杠。验证：2 个 HTTP 场景测试由失败转通过。

## 2. 测试自身错误（10 处，均与产品行为/规范对齐后修正）

- `FrameSplitterTests.LengthField_BigEndian...`：测试数据把「整帧长」字段写成 5（实际 7 字节帧），
  与注释及后续断言自相矛盾，导致断言越界；
- `ModbusWriteSupportBinaryTests`：FC06 帧长期望 13（MBAP7+PDU5=12），与测试自身的字节布局断言及
  Modbus 规范矛盾；
- `PollingInputTests`：响应样本整体偏移 1 字节（MBAP 按 8 字节摆位），解析器读 [7] 得 0 而失败；
- `ModbusTcpOutputPluginTests.StartAsync...`：无监听环境下状态正确为 Recovering，原断言恒为 Running；
- `*InputPluginTests.Dispose_CallsStopAsync`（File/Tcp/WebSocket ×3）：与基类 P0-3 契约
  （同步 Dispose 只取消 CTS、不停机，停机走 DisposeAsync）冲突；
- `WebSocketInputPluginTests.StartAsync_TransitionsToStarting`：断言后台连接循环下的中间态
  （竞态），改为确定性判据；
- 场景测试 `ModbusTcpForwardingScenarioTests`：StartAsync 返回后立即 SendAsync 与建连竞态，
  改为「连接就绪前重试发送」。

## 3. 管道深测抖动：测试 mock 非线程安全（已修复，2026-10-07 当日追加）

`ResilientPipelineDeepTests` 的两个用例曾表现为「稳定失败」——**这个初判是错的，实测是抖动**：
各连跑 5 轮，`ProcessAsync_MessageClonedForEachOutput` 通过 3/5、
`CircuitBreaker_ResetAllowsRetry` 通过 2/5（后者断言 SendCount==4 实得 2）。

根因（测试侧并发缺陷，非产品问题）：
- `RecordingMockOutput.ReceivedMessages` 用**非线程安全的 List.Add** 接收消息，
  而管道按消息并发派发（每条 Task.Run），测试线程随后无屏障读取 → 偶发读到空集合；
- 多个 mock 的 `SendCount++` 是**非原子读改写**，并发派发下丢更新（4 条只计到 2 条）。

定位依据：把相同接线（RegisterOutput×2 + AddRouter + StartAsync + ProcessAsync + WaitForIdle）
写成独立进程探针时**稳定通过**——差别正是探针 mock 用了 `lock`。

修复：`RecordingMockOutput` 改为锁保护 + 快照属性；`ToggleMockOutput` / `FastMockOutput` /
`AlwaysFailMock` 的计数改 `Interlocked.Increment`（同一文件里 SlowMockOutput 早已如此，
说明这是已知坑但未推广）。修复后两个用例各 **5/5 通过**，全量套件连续两轮 1373/1374 稳定。
