# iot-sdk 架构分析与消费者合并建议

> 版本: 2026-09-02  
> 范围: iot-sdk + ZL.PlcSimulator + ZL.Simulator + UseThink.Iot/api  
> 方法: csproj 依赖追踪、代码逐行比对、grep 全仓库引用搜索

---

## 1. 证据摘要：三个消费者的 iot-sdk 使用画像

### 1.1 ZL.PlcSimulator（58 处引用）

**顶层依赖**：
- `PlcSimulator.Core` 引用 `ZL.Watchdog`（NuGet）
- `PlcSimulator.UI` 深度引用 `ZL.ProtocolGateway`（NuGet）

**核心使用点**：
- `PlcToGatewayBridge.cs`：将 `PlcMemory` 数据桥接为 `ZL.ProtocolGateway.Message`，构造 `TagWrite` 到网关
- `IGatewayPipeline`：UI 层抽象接口，解耦 ProtocolGateway 具体实现
- `GatewayOutputPluginFactory`：实现 `IOutputPlugin`，以稳定 Id 接入 Pipeline
- `GatewayForwarder`：将采集的 Watch 数据通过 ProtocolGateway 转发
- `GatewayToolViewModel` / `MainWindowViewModel.Gateway`：UI 状态同步与启动/停止 HttpServer、ModbusServer、MqttSubscriber

**结论**：ZL.PlcSimulator 是 **ProtocolGateway 的上层集成消费者**，通过桥接模式适配，不是重复实现。

### 1.2 ZL.Simulator（198 处引用）

**顶层依赖**：
- `Simulator.Core` 同时引用：
  - `ZL.Framing`（NuGet，来自 iot-sdk）
  - `ZL.ConnectionGuard`（本地 ProjectReference）
  - `ZL.Protocol`（NuGet，来自 iot-sdk）
- `Simulator.Instruments` 同时引用：
  - `ZL.Framing`（NuGet）
  - `ZL.DataProcessing`（本地 ProjectReference）
  - `ZL.Protocol`（NuGet）
  - `ZL.Probing`（NuGet）
- `Simulator.Avalonia` / `Simulator.WinForms` 引用 `ZL.Shared`（本地 ProjectReference）

**核心使用点**：
- `GuardedSerialByteTransport.cs`：使用 `ZL.ConnectionGuard` 管理串口连接，复用原有字节分包
- `ConfigurableProtocolSimulator.cs` / `ScpiSimulator.cs`：使用 `ZL.DataProcessing` 进行数据模板解析和表达式计算
- `AdvancedTemplateProcessor.cs`：使用 `ZL.DataProcessing` 模板引擎
- `AppStructuredLog.cs` / `SecurityMaintenanceService.cs`：使用 `ZL.Shared.StructuredLog` 进行结构化日志记录

**结论**：ZL.Simulator 是 **混合消费者**：上层能力（Framing/Protocol）已通过 NuGet 消费 iot-sdk，但 foundation 四件套（ConnectionGuard/DataProcessing/Script/Shared）仍维护**本地独立副本**。

> **关键发现**：`pipeline.json` 已将这 4 个 foundation 模块列为发布项目（`obfuscate: true`），说明 iot-sdk 已在向 nuget.org 发布这些包。ZL.Simulator 的 P0 切换并非要求 iot-sdk 新增发布流程，而是对齐现有消费者模式。

### 1.3 UseThink.Iot/api（59 处引用）

**顶层依赖**：
- `UseThink.Iot.Core` / `UseThink.Iot.Web` 深度引用：
  - `ZL.IotHub.Core` / `ZL.IotHub.Models` / `ZL.IotHub.Notifications`
  - `ZL.Iot.Interface`
  - `ZL.Iot.Runner.Generator.Core`
  - `ZL.ProtocolGateway`（NuGet）
  - `PlcSimulator.Core.Drivers`（NuGet）

**核心使用点**：
- `DeviceRuntimeService`：基于 `ZL.IotHub.Core.DeviceRoot` 管理设备生命周期
- `PlcHubBridgeService`：将 PLC 事件桥接到 SignalR Hub
- `GatewayHostService`：托管 ZL.ProtocolGateway 生命周期
- `DeviceProtocolSemantics`：协议名兼容映射（UseThink → ZL.IotHub 标准 key）
- `RunnerGenerateEndpoints`：使用 `ZL.Iot.Runner.Generator` 生成 Runner 配置

**结论**：UseThink.Iot/api 是 **iot-sdk 上层能力的纯消费者**，无重复实现。

### 1.4 发布流水线现状

根据 `pipeline.json` 的 `projects` 数组：

| foundation 模块 | 已在 pipeline.json | obfuscate |
|-----------------|--------------------|-----------|

| `ZL.Script` | ✅ | true |

`pipeline.json` 的 `consumers` 中已包含 `UseThink.Iot.api`，说明 iot-sdk 已有跨仓库 PackageReference 消费者的验证经验。

## 4. 合并与优化建议

### 4.1 P0：ZL.Simulator foundation 四件套替换为 iot-sdk NuGet 引用

**目标**：删除 ZL.Simulator 本地 `ZL.ConnectionGuard`、`ZL.DataProcessing`、`ZL.Script`、`ZL.Shared`，改为引用 iot-sdk 发布的 NuGet 包。

**可行性分析**：
- 重复度：100%（逐文件 `diff -u` 结果：ZL.DataProcessing 6 个文件、ZL.Script 5 个文件、ZL.Shared 3 个公共文件内容完全一致；ZL.ConnectionGuard 除 14 处 `.ConfigureAwait(false)` 风格差异外业务逻辑完全一致）
- 风险：**低-中**
  - 功能等价：核心逻辑完全一致
  - `netstandard2.0` 风险已排除：已验证 ZL.Simulator 中仅 `ZL.Script.csproj` 自己声明了 `netstandard2.0`，无其他 `net48`/`netstandard2.0` 消费者项目，可直接删除该目标框架
  - 新增风险：**foundation 四件套在 iot-sdk 内无专属单元测试覆盖**（8 个 tests/ 项目均未引用它们），切换后主要依赖 ZL.Simulator 的消费者测试验证
- 迁移成本：**中**
  - 需要更新 `Simulator.Core`、`Simulator.Instruments`、`Simulator.Avalonia`、`Simulator.WinForms` 的 csproj 引用
  - 需要全量编译 ZL.Simulator 并运行 `Simulator.WebIntegration.Tests` 验证

**推荐动作**：
1. 在 `ZL.Simulator/src/ZL.Script/ZL.Script.csproj` 中删除 `netstandard2.0` 目标框架（无实际消费者，避免不必要的兼容性负担）
2. 确认 iot-sdk 已发布的 NuGet 包版本（`pipeline.json` 已包含这 4 个包），若 ZL.Simulator 需要特定版本则先发布
3. ZL.Simulator 删除 4 个本地项目，改为 `<PackageReference Include="ZL.ConnectionGuard" />` 等
4. 运行 ZL.Simulator 全量编译和 `Simulator.WebIntegration.Tests` 验证

**消费者影响**：
- ZL.Simulator：正向（减少维护成本，自动获得 iot-sdk 的 bug fix）
- ZL.PlcSimulator：无影响
- UseThink.Iot/api：无影响

### 4.2 P1：ZL.Scripting 与 ZL.ProtocolGateway.Scripting 的 LuaScriptEngine 合并

**目标**：将 `ZL.ProtocolGateway.Scripting/LuaScriptEngine.cs` 合并到 `ZL.Scripting`，ProtocolGateway 仅保留上下文绑定适配层。

**可行性分析**：
- 重复度：~80%（核心逻辑一致，差异在上下文绑定和安全加固）
- 风险：**中**
  - `ProtocolGateway.Scripting.LuaScriptContext` 依赖 ProtocolGateway 内部类型（`Message`、`TagWrite`），需要抽象接口
  - `LoadCLRPackage` 安全加固是 ProtocolGateway 特定需求，需要保留为可扩展点
- 迁移成本：**中高**
  - 需要抽象 `ILuaScriptContext` 接口，将 ProtocolGateway 特有类型隔离到 Adapter
  - 需要更新 ZL.ProtocolGateway 的测试和实现

**推荐动作**：
1. 定义 `ILuaScriptContext` 接口（提供 `SetGlobal`、`GetGlobal`、`RegisterAssembly` 等最小必要 API）
2. `ZL.Scripting.LuaScriptEngine` 增加构造函数注入 `ILuaScriptContext` 适配器
3. `ZL.ProtocolGateway.Scripting` 实现 `ProtocolGatewayLuaContext : ILuaScriptContext`，内部转换 `Message`、`TagWrite`
4. 保留 `LoadCLRPackage` 为 `ILuaScriptContext` 的可选安全策略
5. 运行 ZL.ProtocolGateway 全量测试验证

**消费者影响**：
- ZL.PlcSimulator：无直接影响（不直接使用 LuaScriptEngine）
- ZL.Simulator：无影响
- UseThink.Iot/api：无影响

### 4.3 P1：ZL.EdgeService.Biz.DeviceKit 与 ZL.Iot.Plugin.DeviceKit 抽取公共类

**目标**：将两个 DeviceKit 的公共逻辑（动态 DLL 加载、`DriverTypeDic` 维护、设备实例创建）抽取到 platform 层公共类。

**可行性分析**：
- 重复度：~70%（职责重叠，但 I/O 路径已分叉）
- 风险：**中**
  - EdgeService 版本 358 行，支持更多驱动类型和错误恢复
  - Iot.Plugin 版本 123 行，轻量级
  - 抽取时需要保留两个模块的特定扩展点
- 迁移成本：**中**

**推荐动作**：
1. 定义 `DeviceKitCore` 抽象类（platform 层），封装：
   - `DriverTypeDic` 线程安全字典
   - `BuildDeviceConfigFromDto` 公共逻辑
   - 驱动 DLL 动态加载
2. `EdgeService.Biz.DeviceKit` 继承 `DeviceKitCore`，保留 EdgeService 特定 I/O 路径
3. `Iot.Plugin.DeviceKit` 继承 `DeviceKitCore`，保留 Plugin 轻量级实现
4. 更新 `ZL.EdgeService.Tests` 的 `DeviceKitTests`，移除复制私有逻辑的坏味道，改为测试 `DeviceKitCore`

**消费者影响**：
- ZL.PlcSimulator：无直接影响
- ZL.Simulator：无影响
- UseThink.Iot/api：无影响

### 4.4 P2：BizAutoInteract 与 AutoInteract 暂不合并

**理由**：
- 重复度：~60-70%
- I/O 路径已分叉，合并风险高
- 无明确业务需求推动统一
- 建议保持现状，待业务演进到需要统一时再评估

## 9. 结论

1. **最优先行动**：ZL.Simulator 的 foundation 四件套应替换为 iot-sdk NuGet 引用（P0）。代码级 diff 显示为 100% 功能等价，且 iot-sdk 已通过 `pipeline.json` 配置发布这些包，风险可控，收益最大。
2. **次要行动**：iot-sdk 内部 LuaScriptEngine 和 DeviceKit 重复可逐步合并（P1），但需谨慎抽象。
3. **暂不行动**：BizAutoInteract/AutoInteract、PlcToGatewayBridge、DeviceProtocolSemantics 维持现状。
4. **消费者无坏影响**：所有建议均不破坏 ZL.PlcSimulator、ZL.Simulator、UseThink.Iot/api 的现有功能。
5. **前置条件**：实施 P0 前，建议先为 foundation 四件套补充基础集成测试，降低无测试覆盖的切换风险。
