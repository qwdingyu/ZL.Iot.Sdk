# ZL.Framing 超时冲刷「定时器早到」丢帧修复记录

日期：2026-10-04
影响：`src/foundation/ZL.Framing/Core/FrameAssembler.cs`（Timeout 策略）
状态：已修复，回归锁见 `tests/ZL.Probing.Tests/FrameAssemblerTimeoutFlushTests.cs`

## 1. 缺陷

`FrameAssembler.FlushOnIdle` 在定时器「早到」时直接 `return` 而**不重排定时器**：

```csharp
// 修复前
if ((DateTime.UtcNow - _lastReceivedUtc).TotalMilliseconds < _timeoutMs) return;
```

而本类定时器构造为 `new Timer(_ => FlushOnIdle(), null, Infinite, Infinite)`（周期 `Infinite`）。
一旦某次触发比 dueTime 略早（计时器粒度/时钟抖动，属常态而非异常），本次冲刷作废，
且**再也不会有下一次触发**——缓冲区里的帧从此永久滞留：

- 调用方只看到「无响应」，服务端无任何日志，完全静默；
- `Timeout` 是 `ByteFramingOptions` 的**默认策略**，所有未显式配置成帧策略的字节流都走这条路径。

## 2. 证据（对照实验，消费方 ZL.Simulator 侧完成）

用本包源码直接压测（2000 次/组，2026-10-03）：

| 场景 | 修复前 | 修复后 |
| --- | --- | --- |
| 整块投喂 | 丢帧 28/2000（1.40%） | 0/2000 |
| 分片投喂（更贴近真实 TCP 到达） | 丢帧 271/2000（13.55%） | 0/2000 |

结构性策略（FixedLength / LengthField*）不走超时路径，不受影响（500/500 零丢失、0ms 即时成帧）。

## 3. 修复

早到时**重排剩余时间**后再退出（与同仓正确实现保持同一形状）：

```csharp
double idleMs = (DateTime.UtcNow - _lastReceivedUtc).TotalMilliseconds;
if (idleMs < _timeoutMs)
{
    TryChangeTimer(Math.Max(1, (int)Math.Ceiling(_timeoutMs - idleMs)), Timeout.Infinite);
    return;
}
```

重排后最迟再触发一次即可满足阈值，收敛有保证；`TryChangeTimer` 内部已吞并发关闭时的
`ObjectDisposedException`，不影响停机路径。

## 4. 回归锁

`tests/ZL.Probing.Tests/FrameAssemblerTimeoutFlushTests.cs`：1ms 超时 × 50 轮压测，
任何一轮帧未冲刷即失败。注意事项（写给自己人）：

- 该缺陷是时序竞态，单发用例不可靠；1ms 超时下修复前实测约 8%/轮，50 轮漏检概率 <1%；
- 单轮等待上限给了 5s（正常 1~2ms 即冲刷）：xUnit 并行 + 双 TFM 并跑时线程池繁忙，
  回调可能被推迟几百毫秒——那只是**晚到**不是丢帧，上限给窄了会制造假失败
  （第一版 40ms 上限就因此误报过：53/60 轮在 40ms 内没等到回调）。
