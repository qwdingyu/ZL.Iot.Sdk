# iot-sdk 架构分析与合并建议（严谨版）

> 日期：2026-09-02
> 范围：`src/` 下多项目架构、重复能力、边界模糊项

### 1.2 关键观察

- `src/` 内存在 5 个"孤儿模块"：`ZL.ConnectionGuard`、`ZL.Scripting`、`ZL.DataProcessing`、`ZL.Watchdog`、`ZL.Iot.Plugin`。它们不在 src/ 内被任何其他项目 ProjectReference 引用。

## 2. 候选合并项分析（证据驱动）

### 2.1 ZL.Scripting（foundation Lua） vs ZL.ProtocolGateway.Scripting（platform Lua）

- **结论：建议合并。**
- **证据：**
  - 精确 diff（`diff -u` 实测）显示两个 `LuaScriptEngine.cs` 核心逻辑约 80% 相同：
    - 共享 `Lua _lua` 字段、`_lock`、`_disposedInt` 单次 Dispose 模式
    - 共享可取消执行路径：独立 Lua 状态 + Debug Hook 设置 `cancelled` 标志 + `Task.Run` + `Wait(ct)` 双层防护
    - 共享 `ExecuteFile`、`ValidateScript`、`HookInstructionCount = 1000` 常量
  - 差异点仅为上下文绑定层：
    - `ZL.Scripting`：通用 `object context` + `(string luaName, string methodName)[] bindings` 元组绑定，运行时反射
    - `ZL.ProtocolGateway.Scripting`：强类型 `LuaScriptContext` + 静态缓存 `MethodInfo[]` / `string[]` 绑定表
  - 安全差异：`ZL.ProtocolGateway.Scripting` 移除了 `LoadCLRPackage()`（防任意 .NET 类型访问），`ZL.Scripting` 仍保留。
  - 引用关系：`ZL.Scripting` 在 src/ 内无消费者；`ZL.ProtocolGateway.Scripting` 仅被 tests 引用，但其 `LuaScriptOutputPlugin` 在 platform 层使用。
- **风险：**
  - `ZL.ProtocolGateway.Scripting` 的 `LuaScriptContext` 强依赖 `ZL.ProtocolGateway.Message` / `TagWrite` 等内部类型。
  - 若直接合并，foundation 将依赖 platform，违反分层铁律。
- **建议：**
  1. 在 `ZL.Scripting` 中定义 `ILuaContext` 抽象接口，仅暴露脚本需要的最小能力（ topic / timestamp / json / text / hex / state / log 等）。
  2. `ZL.ProtocolGateway.Scripting` 改为薄适配器：`LuaScriptContext : ILuaContext`，将 ProtocolGateway 的 Message/TagWrite 映射到接口。
  3. 保留单一 `LuaScriptEngine` 实现于 foundation，接受 `ILuaContext`。
  4. 将 `ZL.ProtocolGateway.Scripting` 的安全加固（移除 LoadCLRPackage）上移到 foundation 统一实现。
- **业务价值：**
  - 消除 2 套 Lua 引擎维护成本。
  - `ZL.Scripting` 当前无测试，合并后可复用 `ZL.ProtocolGateway.Tests` 的测试资产反向覆盖 foundation。

### 2.2 ZL.EdgeService.DeviceKit vs ZL.Iot.Plugin.DeviceKit

- **结论：建议合并（抽取公共内核）。**
- **证据：**
  - 两个项目都定义了同名类 `DeviceKit`，核心职责相同：动态加载驱动 DLL、维护 `DeviceList` / `DriverTypeDic`、创建驱动实例。
  - `ZL.EdgeService/Biz/DeviceKit.cs`：358 行，支持数据库驱动列表、远程下载 DLL、多构造函数重载、支持 `IPlcDriver` 和 `DeviceBase` 双接口检测、异步连接启动。
  - `ZL.Iot.Plugin/DeviceKit.cs`：123 行，仅支持本地目录扫描、`IPLCDriver` 接口、同步 `Activator.CreateInstance`。
  - 关键方法重叠：
    - `GetInstance()`：两者都是单例/多实例字典模式。
    - `DownAndLoadDrivers()`：两者都扫描 assembly → 查找驱动类型 → 加入 `DriverTypeDic`。
    - `CreateDriver()` / `CreateInstance()`：两者都通过 `Activator.CreateInstance` 或构造函数注入创建驱动。
  - `ZL.EdgeService.Tests/DeviceKitTests.cs` 的注释明确写着 `辅助方法（复制 DeviceKit 中的逻辑）`，把 `BuildDeviceConfigFromDto`、`ParseIntFromJson` 等私有方法复制到测试中，说明 `DeviceKit` 内部逻辑已经复杂到需要测试，但又因是私有方法导致测试无法直接调用——这是典型的“应该抽取公共类”的信号。
- **风险：**
  - `ZL.EdgeService.DeviceKit` 依赖数据库服务（`IotDriverService`、`IotEdgeRelationService`）和 HTTP 下载，而 `ZL.Iot.Plugin.DeviceKit` 是纯本地加载。
  - 两个 `DeviceKit` 创建的驱动实例类型不同：EdgeService 偏向 `DeviceBase`，Iot.Plugin 偏向 `IPLCDriver` + `IDev` 包装。
- **建议：**
  1. 抽取 `ZL.Platform.DeviceRuntime`（或类似命名）公共类库，只保留最稳定的能力：assembly 扫描、类型注册、实例创建。
  2. `ZL.EdgeService.Biz.DeviceKit` 继承/组合公共内核，扩展数据库驱动列表和下载能力。
  3. `ZL.Iot.Plugin.DeviceKit` 继承/组合公共内核，保留本地目录扫描和 `SimpleInteractWrapper` 适配。
  4. 将 `DeviceKitTests` 中的复制逻辑删除，改为直接测试公共内核类。
- **业务价值：**
  - 消除两个同名类的认知负担。
  - 修复“测试复制私有逻辑”的坏味道，提升驱动加载链路的可测试性。

### 2.3 ZL.EdgeService.BizAutoInteract vs ZL.Iot.Plugin.AutoInteract

- **结论：不建议直接合并，但建议抽取公共基类。**
- **证据：**
  - 两者都继承 `ZL.IotHub.Core.DeviceBase`，都用于“将旧版业务逻辑桥接到新 PlcBase 架构”。
  - `ZL.Iot.Plugin/AutoInteract.cs`：
    - `BatchReadLoop` 空转等待
    - `OnTriggerDataChange` → `HandleDataChange` → `ExecutePlanLogic`
    - 使用 `DeviceKit.CreateDriver` 进行实际 I/O
    - `WirteGeneral2Plc` 调用 `EnqueueNormalWriteAsync`
  - `ZL.EdgeService/Biz/BizAutoInteract.cs`：
    - `BatchReadLoop` 空实现 `Task.CompletedTask`
    - 订阅 `OnTagValueChanged` → `HandleLegacyDataChange`
    - 直接使用 `HslCommunication.IReadWriteNet` 进行 I/O
    - `WriteList` 调用 `EnqueueNormalWriteAsync`
  - 相似度约 60-70% 在“桥接模式”上，但具体 I/O 路径和业务触发逻辑已经分叉。
- **风险：**
  - `ZL.Iot.Plugin.AutoInteract` 仍使用 `InteractInfoList`（`List<dynamic>`）保存业务配置，类型不安全。
  - `ZL.EdgeService.BizAutoInteract` 已进化为支持 `PLAN/SCAN/BOM` 等多种触发器，但代码中仍是示例占位。
- **建议：**
  1. 抽象 `LegacyBizBridgeBase : DeviceBase`，提炼共性：事件订阅、 legacy args 适配、WriteList 转发。
  2. `ZL.Iot.Plugin.AutoInteract` 和 `ZL.EdgeService.BizAutoInteract` 作为具体子类，各自实现 I/O 细节。
  3. 明确 `ZL.Iot.Plugin` 的维护策略：如果确定废弃，应在代码头加 `[Obsolete]` 和迁移指引；如果保留兼容，应补 tests。
- **业务价值：**
  - 减少两个文件之间的认知切换成本。
  - 为未来“所有工站自动交互”提供统一扩展点。

### 2.4 ZL.DataProcessing（foundation）— 孤儿模块

- **结论：不是重复项，但是高风险孤儿模块，需明确处置。**
- **证据：**
  - 全仓库搜索 `using ZL.DataProcessing`，在 `src/` 下 **0 匹配**。没有任何 src/ 项目引用它。
  - 全仓库搜索 `using ZL.Scripting`，在 `src/` 下 **0 匹配**。
  - `ZL.DataProcessing` 无专属测试项目。
  - 代码内容：
    - `DataExpressionEngine`：基于 `ZL.Script` 的表达式求值、Session/State 管理、模板插值
    - `TemplateParser`：解析 `${expr}` / `@{stmt}` 模板语法
    - `HexCodec`：十六进制规范化、字节转换、校验和剥离
    - `PatternMatcher` / `ScriptHelpers`：规则匹配与脚本辅助
  - `ZL.Script/Industrial/IndustrialHelpers.cs` 的注释甚至写着 `#region Base Algorithms (Ported from ZL.DataProcessing for 100% compatibility)`，说明 DataProcessing 的算法曾向外复制扩散。
- **风险：**
  - 无消费者、无测试，代码腐烂风险极高。
  - 若外部消费者已引用，删除会破坏兼容性。
- **建议：**
  1. 优先排查外部消费者（UseThink.Iot / PcStationIot）是否直接引用 `ZL.DataProcessing`。
  2. 若无外部引用：将其标记为 `[Obsolete]`，并将 `DataExpressionEngine` / `TemplateParser` 能力内聚到 `ZL.Iot.Runner` 或 `ZL.EdgeService` 的实际使用点。
  3. 若有外部引用：维持现状，但必须补 tests，并明确文档标注“稳定维护但无 src/ 内消费者”。
- **业务价值：**
  - 消除“代码在仓库里但没人用”的隐形技术债。
  - 避免未来重构时踩到无人维护的暗雷。

### 2.5 ZL.Script（DynamicExpresso） vs ZL.Scripting（NLua）

- **结论：不建议合并。**
- **证据：**
  - `ZL.Script`：C# 表达式/模板解释器，面向规则脚本、模板插值、工业助手库（Hex/Binary/Crc/Format）。被 `ZL.DataProcessing` 引用。
  - `ZL.Scripting`：Lua 5.1 脚本引擎，面向复杂流程脚本和插件化扩展。
  - 两者在 `ZL.DataProcessing` 中被共同使用，说明业务上需要两种脚本能力并存。
- **建议：**
  - 维持双引擎。
  - 未来可在 `ZL.Iot.Interface` 中统一抽象 `IScriptEngine`，让上层不感知语言差异，但底层实现保持分离。

---

### 2.6 ZL.DataConvert（platform） vs ZL.DataProcessing（foundation）

- **结论：不建议合并。**
- **证据：**
  - `ZL.DataConvert` 面向 PLC 点位类型转换（Byte/Int/Float/Double/Long/ULong/String/Hex/ByteArray），是工业协议现场数据解释的基础工具。
  - `ZL.DataProcessing` 面向消息模板解析、表达式求值、Session/State 管理，是数据后处理与规则解释器。
  - 虽然 `ZL.DataProcessing.HexCodec` 与 `ZL.DataConvert.StringLib` 存在十六进制工具重叠，但调用场景不同：
    - `HexCodec` 用于表达式引擎内部的 hex 字符串规范化
    - `StringLib.GetHexStringFromByteArray` 用于 PLC 字节数组的可视化
  - `ZL.DataConvert` 有明确消费者 `ZL.Dao.Edge`。
- **建议：**
  - 维持分层现状。
  - 若后续出现字节工具重复调用，抽取极小共享工具（如 `HexNormalize`）到 `ZL.Shared`，不要合并项目。

---

### 2.7 ZL.Connection + ZL.ConnectionGuard vs ZL.Watchdog

- **结论：不建议合并。**
- **证据：**
  - `ZL.Connection`：仅 3 个文件（`ConnectionState.cs`、`ConnectionStateMachine.cs`、`ExponentialBackoffStrategy.cs`），核心是连接状态机与指数退避。无 src/ 内直接消费者（除 tests）。
  - `ZL.ConnectionGuard`：约 30 个文件，包含 10+ Adapter（Tcp/Serial/Can/Lin/Udp/Http/Hsl/ModbusTcp 等）、心跳策略、发送锁、状态事件队列。`ConnectionGuard.csproj` 显式引用 `ZL.Connection`。
  - `ZL.Watchdog`：6 个文件，通用组件健康检查 + 自动重启，面向任意 `WatchedEntry`（HealthCheck + Restart 委托）。
  - `ZL.ConnectionGuard` 已内置 `DeviceDeadTimeoutMs` 看门狗和 `ShouldSendHeartbeat` 心跳机制，但这是连接生命周期的一部分，不能替换为外部 `WatchdogService`。
- **建议：**
  - 维持现状。
  - 若 EdgeService 未来需要监控“多个不相关组件”（如数据库、MQTT 客户端、文件写入器），再把 `ZL.Watchdog` 提升为平台级组件。

## 3. 边界模糊项

### 3.1 ZL.EdgeService vs ZL.Iot.Plugin — 整体边界

- **现状：**
  - `ZL.EdgeService` 是当前主产品线，深度集成 `ZL.IotHub`，拥有 `EdgeExecutorKernel`（原子快照、Tag 触发、写队列）、完整 DI 容器、HslCommunication 直连驱动。
  - `ZL.Iot.Plugin` 是旧兼容/插件化驱动容器，拥有 `DeviceKit`（动态 DLL 加载）、`AutoInteract`（旧业务桥接）、`SimpleInteractWrapper`（`IPLCDriver` → `IDev` 适配）。
  - `ZL.Iot.Plugin/Config.cs` 的日志前缀写死 `"ZL.EdgeService"`，说明历史上两者曾是一个项目。
  - 当前两者无 csproj 交叉引用，但 EdgeService 的 tests 跨边界测试了 Iot.Plugin 的 `DeviceKit` 逻辑（复制粘贴版）。
- **判断：**
  - 不建议整体合并。`ZL.Iot.Plugin` 的“插件化动态加载”能力对某些现场场景仍有价值。
  - 建议走“能力抽取 + 明确主次”路线，而非“吞并”。
- **建议：**
  1. 明确 `ZL.Iot.Plugin` 为“Legacy Plugin Compatibility”组件，文档标注维护状态。
  2. 将 `DeviceKit` 公共内核抽取到 platform 层（如 2.2 所述）。
  3. 将 `AutoInteract` 桥接基类抽取到 `ZL.Iot.Interface` 或 domain 层。
  4. 逐步将 `ZL.EdgeService` 的测试复制逻辑（`DeviceKitTests.cs` 中的私有方法复制）改为直接调用抽取后的公共类。

---

### 3.2 ZL.Watchdog vs ZL.ConnectionGuard 内置看门狗

- **现状：**
  - `ZL.Watchdog`：通用 `WatchdogService`，接受 `WatchedEntry`（`HealthCheck` + `Restart` 委托），支持滑动窗口限流。
  - `ZL.ConnectionGuard`：内置 `DeviceDeadTimeoutMs`（长时间无接收则重连）和 `ShouldSendHeartbeat`（心跳保活）。
- **判断：**
  - 观察窗口不同：Watchdog 观察“组件是否存活”，ConnectionGuard 观察“连接是否存活”。
  - 不建议合并。
- **建议：**
  - 维持现状。
  - 若 EdgeService 需要“监控数据库/MQTT/文件写入器”等多组件，再把 `ZL.Watchdog` 提升为平台级，此时可让 `WatchdogService` 内部委托 `ConnectionGuard` 状态作为其中一个 `WatchedEntry`。

## 6. 实施约束与原则
